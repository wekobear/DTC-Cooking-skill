# DTC Cooking：一句话检查页面，做出能落地的改进方案

> 版本 0.3.0｜这份说明解释 Skill 如何开展工作，不是某个站点已经改版、上线或提升转化的记录。

![流程图](assets/workflow.png)

[交互流程图](workflow.html)（下载后用浏览器打开）

核心目标很简单：帮助 DTC 独立站看清自己的页面哪里让顾客看不懂、选不定、买不顺，再给出有依据、能实施的改进方案。页面好看只是其中一部分，更要让顾客更容易理解商品、放心购买。

## 1. 用户先说一句话

例如：“帮我检查这个商品页的手机端体验，给出修改方案，做好页面并上线。”系统先确认站点和本次范围。只想找问题，就交付问题与方案；想改页面，就继续制作和验证；明确要求上线且条件具备，就推进到线上检查。已经给过的信息不重复问。

启动时还会询问是否开启多智能体协作。开启后，可以让不同助手分别看资料、查标杆、写方案、做页面和验收，由主助手汇总；关闭也按同样标准完成。能独立做的事情并行，依赖上一步结论的事情按顺序做。

## 2. 有哪种资料，就走哪条路

**第一条：已经连接后台。** 先检查 PostHog、GA4 或商城后台是否连接到正确站点，再读取与本次页面有关的信息，了解顾客在哪里犹豫或停止操作。只装了工具，不代表已经能读到这个站点的数据。

**第二条：没有连接，但有现成资料。** 可以建议连接已有的分析工具或商城后台；暂时不连接时，PDF、表格、经营报表、数据文档和截图都可以。先看清资料来自哪里、是什么时候、说的是哪个页面，再提取对方案有用的发现。不必为了开始检查而强制接入后台。

**第三条：什么资料都没有。** 直接检查用户的真实独立站，再选择相关跨品类标杆做对照。说明“你的页面现在怎样、标杆怎样处理、建议怎么改、为什么值得试”。这种路线可以提出明确方案，但不能把猜测写成真实流失原因，也不能编造提升比例。

## 3. 找出最值得先改的问题

实际打开页面，检查手机和电脑上的阅读、选商品、查看保障、加入购物车等过程。每个问题附上真实截图，用一句话说明它可能怎样影响购买，并排出先后顺序。

标杆从可配置的公开清单按问题选择，例如参考 DJI 的商品比较、Anker 的场景选购、Casper 的购买保障。只选与本次问题有关的案例，不机械检查全部品牌。必须打开具体页面并保存真实截图，解释借鉴什么、哪里不适合照搬。

## 4. 把方案写成能看懂的说明书

产品 PRD 可以直接叫“页面改进说明书”。它要讲清本次改哪里、发现什么问题、证据是什么、准备怎么改、如何判断做对了。

有数据就放相关资料和必要截图；没有数据就明确写“根据页面与标杆对照提出”。同时放入用户页面与标杆的真实截图，逐项解释建议。价格、优惠、保障和商品能力以用户确认的信息为准。

## 5. 先把页面做出来，再选择怎样修改

按 Vibe Designing Playbook 的方法，先安排信息顺序、主要按钮、手机和电脑的布局，以及加载或出错时的提示；再使用 HeroUI 的组件来制作可操作的页面。沿用现有品牌规范，不为了换外观重做整站。

网页预览完成后，让用户选择交付方式：有 Figma，可以导入可编辑设计稿；使用 Codex 时先检查 Figma 插件，缺少时提示安装并验证连接，再按用户选择导入。没有 Figma 但想自己调整，推荐 [pen.dev 客户端](https://www.pen.dev/)；也可以直接交付 HTML + Tailwind CSS。

pen.dev 支持导入网页、手动修改和导出页面代码，适合调整文字、图片与排版，但不能把导出页面当成已经接好全部购买功能。用户修改后，要重新检查手机、电脑上的展示和关键操作。

## 6. 检查完成，再按要求交付或上线

实际点击和操作页面，检查商品信息、按钮、购物车及相关购买流程。需要记录顾客操作时，确认记录能被后台收到。只看到“构建成功”或预览正常，不能说明线上页面已经可用。

发布前核对正确站点与发布目标，发布后重新检查线上页面，并留下恢复旧版本的方法。缺少必要授权或账号访问时，说清还差什么；能独立完成的准备继续做。

## 7. 每个大阶段都留下可审核的结果

启动、资料整理、界面与标杆研究、方案、页面设计、开发验收和上线检查，各自留下简短报告。报告先回答“做了什么、发现什么、建议什么、还有什么没确认”，配上必要截图和结果链接。不把没执行的步骤写成完成。

最终交付包括改进说明书、前后对比、可查看或修改的页面，以及实际完成的检查结果。上线后观察顾客是否更容易完成关键操作；“已经上线”和“确实提升转化”分开说明，有后续证据再判断效果。
