# 从检查页面到交付上线

按当前任务终点使用本文件：检测到方案、原型到预览、上线到生产验证。普通步骤不增加审批；用户已经明确要求的同一操作不重复询问。

## 1. 建立任务记录

记录目标站点/页面、市场与语言、用户要完成的购买任务、现有材料、明确约束、本轮终点和已有授权。先读可用上下文再提问，不要求用户填写所有技术字段。

资料状态尚不清楚时可合并询问：

> 你已有 PostHog 或 GA4，并且连接给当前 AI 了吗？没有连接也可以提供后台报表、PDF、表格或截图。都没有的话，我会直接对照你的页面与相关标杆给方案。是否希望开启多智能体，让不同助手分别处理研究、方案、设计和验收？

工具已验证到正确项目时直接说明会读取什么，不重复问连接状态。新连接若需要用户登录，只说明实际所需动作；继续不依赖连接的工作。不要求密码或完整客户明细。

## 2. 用现有资料形成证据

### 路线 A：连接数据

检查四层状态：可调用工具、授权、目标站点对应项目、相关时间段和事件可用。连接或身份检查成功不能代替目标数据检查。

- PostHog：事件漏斗、路径和错误；已有会话回放可帮助解释具体行为，一段回放不能代表全部顾客。
- GA4：来源、落地页、设备及正确采集的商品/购买事件；先核实实际事件映射，再解释漏斗。
- 商城后台、订单 API、只读数据库：商品、订单、支付、折扣和退款事实；只读与任务有关的字段，不将交易表当作前端行为记录。

在技术附录保留足以复核的口径：域名与项目/property、日期及时区、币种、统计单位和样本量、事件/漏斗窗口、设备或来源分组、缺失/重复及更新时间。需要对账时解释后台与分析平台的差异，不强行令两者相等。

数据不足、采集错误或样本太少，先降低相关结论的确定性；仍可处理已复现的界面问题。不要把每一个采集缺口都机械定为最高优先级。

### 路线 B：用户材料

接受 PDF、CSV/XLSX、数据文档、现成经营报表和截图。先确认内容可读取，以及其来源、日期、统计对象和页面；按文件名与页码、工作表或截图编号引用。只有汇总数字时不推算不存在的用户路径；不把截图中难以辨认的数字写成事实。

建议接入现有 PostHog/GA4；若需要交易事实，可建议补充商城后台或只读数据库。连接不是开始检查的前提，资料可先支持当前方案。只有确实影响结论的缺口才追问。

### 路线 C：没有数据

直接在实际站点完成目标购买任务的观察，选相关标杆逐项对照：

> 用户页面现在怎样 → 标杆怎样处理 → 推荐改成怎样 → 为什么值得试 → 怎么检查。

给出明确的页面结构、文案、交互或信息调整，不把“缺数据”变成空洞建议。报告写明“本轮按页面与标杆对照”；不编造跳出率、流失人数、增长比例或已证明的原因。

## 3. 页面研究与问题排序

围绕当前范围检查手机和桌面关键状态，记录具体元素、复现动作、真实截图和来源。完整任务可覆盖首页、分类/集合、代表商品页、购物车/结账入口和保障信息；单页任务检查该页及直接受影响路径即可。

从 [标杆池](benchmarks.md) 或用户指定资料选择案例。将现站截图和标杆截图放在一起解释，分别标明观察事实与借鉴判断。观察到按钮失效可直接列为缺陷；“更清楚的对比可能帮助选品”属于待验证假设。

优先处理阻断关键操作、令人误解商品/价格/保障，以及有较强证据支持的问题。结合影响范围、证据确定性和实施成本说明排序，不用貌似精确的分数替代判断。

## 4. 页面改进说明书（PRD）

沿用统一问题编号与证据编号。正文先让非技术用户看懂，查询细节和组件参数放附录；没有数据的章节说明缺口，不留下空白数字表。

1. **这次要解决什么。** 页面、顾客任务、范围和交付终点。
2. **现在的问题。** 现站截图、可复现事实、对应问题编号，以及为什么影响理解、选择或下单。
3. **依据是什么。** 实际读取的数据或文件摘录、日期与来源；没有数据则说明页面观察范围。讲清依据如何改变优先级。
4. **别人怎样处理。** 嵌入所选标杆的真实截图，附具体 URL、采集日期、设备/视口、状态；解释可迁移机制和不适用之处。
5. **推荐怎么改。** 页面区块与信息顺序、主要动作、商品/优惠规则、文案素材、双端差异、加载/空/错误状态。默认一个推荐方案，有实际取舍才给备选。
6. **怎样做、怎样查。** 对应组件或页面、真实接口与模拟边界、需要沿用或补充的事件、可操作的验收动作及预期结果。
7. **还有什么没确认。** 缺少的业务事实、访问权限或证据；标明是否阻塞当前终点。

PRD 里的截图必须能查看。只有品牌名、首页链接或“待补截图”不算完成所需研究；确实受阻时说明受阻证据，选择可核验的替代案例。

## 5. 分工与阶段报告

用户选择开启多智能体后，为实际执行的大节点分配阶段助手。资料分析和标杆研究可并行；方案依赖证据，设计依赖方案，开发依赖规格，验收依赖运行版本，发布依赖验收和对应授权。不要让下游助手猜测上游结论。

| 节点 | 简短产物 | 完成依据 |
| --- | --- | --- |
| 启动 | 任务与资料说明 | 对象、终点、连接/材料状态、协作选择明确 |
| 资料整理 | 数据或材料报告 | 来源和不足可追溯；无数据时并入研究报告 |
| 页面与标杆 | 界面研究报告及截图 | 问题可定位、案例可核验、借鉴边界明确 |
| 产品方案 | 页面改进说明书 | 问题、证据、改法和验收相互对应 |
| 设计 | 页面与组件说明 | 双端、关键状态、内容和组件选择明确 |
| 实现 | 代码、预览和实现说明 | 可运行；真实功能与演示内容分清 |
| 验收 | 检查结果及前后对比 | 实际操作结果支持本次需求 |
| 可编辑稿（可选） | Figma 链接或 pen.dev 材料 | 实际可编辑范围及导出后检查明确 |
| 发布 | 线上检查与恢复说明 | 正确目标/版本、关键路径、恢复入口可核验 |

主助手统一输入版本、问题/证据编号和写入范围，避免多人覆盖同一文件或画布。每次交接附产物、实际检查结果和剩余问题；需求变化只更新受影响内容。资源不足时顺序执行；关闭协作或平台不支持时由单助手完成同样交付。

报告可按任务大小合并为独立章节，保留每个实际大节点结果；用户阅读版只需要“做了什么、发现什么、建议什么、还有什么没确认”。

## 6. 验收、发布与恢复

实现方式与可编辑稿见 [设计与交付](design-and-delivery.md)。完成后按需求验收，不把以下不同层次混成一个“通过”：

| 层次 | 需要的证据 |
| --- | --- |
| 静态/构建 | 实际执行命令和结果；只证明覆盖到的代码或文本规则 |
| 浏览器 | 手机与桌面实际渲染、关键状态及操作；相关的键盘/触控反馈 |
| 业务功能 | 商品、价格、库存、变体、折扣、购物车和受影响购买路径与实际接口一致 |
| 数据采集（涉及才做） | 事件触发/去重、正确项目和平台接收；请求已发出不等于平台收到 |
| 生产 | 发布后的正确域名与版本，受影响页面/资源和关键路径实际可用 |
| 转化效果 | 上线后的可比较数据；上线和功能通过不能证明增长 |

支付等会产生真实订单或费用的动作使用测试环境、测试模式或已有相应授权；未执行部分明确记录，不为凑齐检查下真实订单。

已要求上线时，先核对仓库/站点、生产分支或发布目标、必要配置和当前可恢复版本。沿用项目的发布方式，不因本地预览可用就跳过生产配置。缺少权限或登录时，明确实际缺口，交付已经验证的代码/预览和恢复准备；不得宣称已上线。

发布后读取部署结果并打开生产页面，确认正确版本和受影响操作。失败先判断实际线上状态再重试，避免重复副作用。记录恢复到哪个已知可用版本、从哪里操作；实际恢复使用已有授权或取得缺少的具体授权。

最终说明完成到哪一步，提供产物链接、关键检查和未完成项。需要持续观察时可给出观察方案；定时监控或后续自动执行需要对应请求，不能凭本流程自行建立持续任务。
